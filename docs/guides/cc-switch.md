# CC Switch：日常管理入口

日期：2026-11-05。按已批准的[个人工具箱方案](../design/2026-11-05-personal-ai-toolbox-plan.md)编写，适用已安装的 CC Switch 4.0.25；无需为了使用本指南重新安装。此前版本核验见[历史记录](../validation/2026-11-05-foundation-and-pilot.md)，本轮实际配置与客户端演示结果统一看[配置验收记录](../validation/2026-11-05-toolbox-rollout.md)。下面是操作教程，不代表全部 GUI 步骤已在本机实测。

## 本轮已经确认的范围

以下根据 2026-11-05 的配置执行回报整理；本次指南更新没有重新执行这些操作。

| 项目 | 已确认 | 尚不能据此认定 |
| --- | --- | --- |
| Playwright、Context7 纳管 | 已通过 CC Switch 官方 deep link 导入，目标为 `apps=codex,dsh` | 两个客户端已经在对话中调用成功 |
| Codex 配置识别 | 正常使用环境中的 `codex mcp get` 能识别这两项配置 | 当前对话已经发现或调用它们的工具 |
| DSH 配置落地 | web、desktop 的 YAML 配置均已有对应条目 | 两个界面都已刷新并完成调用 |
| Playwright 服务演示 | SDK 检出 25 个工具，导航、截图成功 | Codex、DSH 的完整对话任务通过 |
| Context7 远程服务演示 | 无 API key 的本次连接检出 2 个工具，Express lookup 成功 | 无密钥访问永久可用、没有额度限制，或客户端任务已通过 |
| 普通技能分发 | 原生 Skills 开关已将 `grilling`、`grill-me` 启用到 DSH，哈希一致 | DSH 已在对话中使用这些技能完成任务 |
| PLC 技能范围 | 保持仅 Codex 启用 | 要为统一管理而扩展到 DSH |

**下一步是刷新客户端并完成短例。** Codex、DSH 的完整对话内调用仍待验证；不需要重新导入现有服务或重复启用已有技能。普通配置采用必要备份、现成入口和公开/合成材料的短演示即可，无需先搭虚拟机、独立账户或复杂隔离环境。

## 先记住在哪里操作

| 要做的事 | 入口 | 管理边界 |
| --- | --- | --- |
| 查看模型、供应商连接 | CC Switch 中对应客户端的供应商页面 | 沿用已有可用供应商；整理工具时不顺带切换模型、路由或账号 |
| 添加、启停 MCP | 官方 deep link 导入后在 CC Switch → MCP 管理，也可用原生添加入口 | 按客户端分别启用；连接检查后仍要在智能体对话中实际调用 |
| 管理普通独立 Skills | CC Switch → Skills | 核对来源、备份后接管；同一份技能只由一个管理器更新 |
| 管理全局提示词 | CC Switch → 提示词，选择对应客户端 | 先保留已有规则，再合并；不要直接用示例覆盖全局 `AGENTS.md` |
| 更新 Superpowers、原生办公插件 | 所属客户端的原生插件入口 | 保持整包安装及其依赖；不把插件内技能再次导入 CC Switch |
| 打开独立应用或完整项目 | [使用卡](../../recipes/README.md)指向的官方入口 | Understand-Anything、Presenton 等由各自原生方式管理 |

第一次整理前，按[备份与换机说明](migration.md)保存私有备份；只调整这次需要接管的项目。不要重置应用、导入整份他人供应商配置，或直接修改 CC Switch 数据库。

## 把已有普通技能交给 CC Switch

适用对象是独立技能目录，包括自行维护的普通技能。能看到 `SKILL.md` 不代表它就是独立安装：先确认来源、原管理者，以及是否依赖插件提供的脚本或工具。

已纳管的 `grilling`、`grill-me` 日常直接在 Skills 列表使用对应客户端开关；无需重走导入步骤。PLC 技能继续保持 Codex-only。以下步骤用于尚未纳管的普通技能，不能把“支持两个客户端”理解为每项都必须双端启用。

1. **先选范围。** 在私有清单中记下技能名称、来源和原管理者，备份完整技能目录（包括其需要的脚本、模板和资源）。原生插件内部技能及完整产品附带技能不勾选；来源不明或同名冲突的先保持原状。本地 `grilling` 也不能仅凭名称认定为某个上游版本。
2. **打开原生导入。** 进入 **Skills → 已安装 → 导入已有**。若界面将入口收在添加菜单中，选择导入本机已有技能的操作；不要改用从仓库重新安装同名技能来代替接管。入口表述以该版本实际界面为准。
3. **从扫描结果逐项选择。** 核对名称与来源目录，只导入已确认的普通技能。导入涉及管理器保存技能及后续向客户端同步，不只是给原目录加一个标签；不要同时移动或删除旧目录。若扫描不到，先用[故障处理](troubleshooting.md)检查，不去复制插件缓存。
4. **检查目标客户端。** 在已安装列表中核对该项，为约定使用的 Codex、DSH 分别设置启用状态。导入列表可见不等于客户端已经加载；已有 `required_targets` 保留原要求，单端问题单独记录。
5. **开一个新对话做小演示。** 从该技能使用卡选一段公开或合成输入，明确要求使用该技能，核对是否实际读取技能并完成示例。只确认名称可见时记为“已发现”；完成任务后才记为“该端演示通过”。
6. **明确接管结果。** 接管成功后，这份技能的分发、启停由 CC Switch 负责；停止 Skills CLI 或旧同步流程对同名技能的更新。Skills CLI 程序可以保留。导入的本地技能若没有可核对的上游来源，就保留人工维护来源，不假定能自动拉取更新。

日常停用时，在 Skills 列表关闭相应客户端的开关，再开新对话确认；要卸载时，先看界面确认框影响哪些客户端和文件。更新前保存本地改动，按已登记来源操作，再重复短演示。不要靠两套管理器互相覆盖来“同步”。

## MCP：先配置，再验证实际调用

**已纳管服务：**当前 Playwright、Context7 已通过官方 deep link 导入，直接进入 CC Switch → MCP 查看、编辑或启停。需要排查时先检查现有条目，不重复添加。

**客户端已有、尚未纳管的服务：**进入 MCP 页面，使用“从现有配置导入”（若界面简称“导入”，选择对应已安装客户端），核对服务名称、传输方式和目标客户端，避免重复添加同一服务。保留已有正常连接及其私有参数。

**新增或换机补齐：**先看[无密钥配置说明](../../configs/README.md)以及 [Playwright](../../configs/mcp/playwright.json)、[Context7](../../configs/mcp/context7.json) 示例。可以打开已核查来源提供的官方 deep link，在 CC Switch 中核对服务配置及目标客户端后导入；本轮这两项使用的是 `apps=codex,dsh`。也可在 MCP 页面点“添加服务器”，按说明填写配置；只复制指定的配置段，不把仓库的说明字段一并当作客户端配置。导入链接如含本机路径或认证参数，也应留在私有位置。

本地命令的路径、环境变量及可能需要的认证在本机填写，不能把占位符原样当成已配置。npm 方案使用已经记录的精确版本及 integrity，不将示例改成 `latest`。公开示例不保存个人绝对路径、令牌或真实请求头。

保存后按以下顺序检查：

1. 在该服务的客户端开关中核对 Codex、DSH 的启用状态。
2. MCP 页点 **检查连通性**，或在单个服务的菜单中点 **测试连接**。4.0.25 的此项检查验证 MCP 握手，不代表智能体已经使用工具。
3. 在目标客户端重新打开会话，确认能发现该服务提供的工具。
4. 在每个约定客户端分别执行一次短演示，检查对话中的工具调用及返回结果，而不只看模型是否给出答案。

本轮服务端 SDK 演示已经成功，继续从客户端刷新和对话短例开始即可。Codex 的配置识别、DSH 的 YAML 条目及 SDK 调用结果分别保留证据；它们不能合并成两个 agent 的 `task-passed`。

浏览器演示可以直接使用：

```text
请使用已配置的 Playwright MCP 打开 https://example.com，读取页面标题与主标题。
说明实际调用了哪个工具；若没有可用工具或打开失败，请直接说明，不凭记忆补答案。
```

Context7 演示可以使用：

```text
请使用 Context7 查询 Vite 的 server.port 配置，说明检索到的文档版本或分支，
给出最小配置例子和来源。若需要认证、额度不足或工具不可用，请说明失败步骤。
```

只用公开页面或合成材料即可，不需要提供真实项目才算能用。DSH 的 MCP 传输需匹配其支持的 stdio 或 Streamable HTTP；旧 SSE 地址不能只改类型名称就当成可兼容连接。

## 提示词和供应商怎样保留

供应商页面先选对客户端，查看当前配置即可；增加技能和 MCP 不要求切换已有供应商。确需改变连接时，先在本机备份并确认目标服务，再单独调整。

提示词也按客户端区分。先保留已有全局规则，在本地整理“原内容 + 需要补充的规则”，审阅后再使用提示词页面的保存/启用操作。启用模板可能改写客户端的全局规则文件，不能用一段演示提示词覆盖全局 `AGENTS.md`；暂不需要修改时，继续沿用现有规则。

## 怎样读状态

来源锁定、`installed`、`CLI-checked`、`agent-discovered`、`task-passed` 分开记录：只记录 `observed_commit` 不等于锁定安装来源；来源锁定不等于安装；安装不等于命令可运行；命令或 MCP 握手成功不等于智能体发现；发现也不等于示例完成。Codex、DSH 分别写结果；尚缺的一端保留待验证，不删减要求。
