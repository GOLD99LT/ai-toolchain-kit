# 常见问题：原因与处理步骤

日期：2026-11-05；CC Switch 4.0.25。先对照[管理指南](cc-switch.md)及[配置验收记录](../validation/2026-11-05-toolbox-rollout.md)，区分尚未配置、连通成功与实际任务通过。以下是排查方法，不声称这些故障或全部 GUI 修复步骤已在本机复现。

当前两项 MCP 已完成官方 deep link 导入，正常环境的 Codex 配置识别、DSH web/desktop 配置条目和服务端短演示均已有结果。剩余重点是刷新客户端后的对话短例；不要因此重复安装，或把复杂隔离环境作为继续验证的前提。

## Skills 导入列表找不到技能

**可能原因：**它已被管理、源目录不在当前扫描范围、目录结构不符合要求，或者它本就属于原生插件/完整产品。

**处理：**Skills → 已安装，先查已有条目；再打开“导入已有”，核对扫描结果中的来源。只对普通独立技能检查完整目录及 `SKILL.md`，不要仅凭缺失名称从插件缓存复制文件。如果当前页面没有提供对应目录的导入方式，先保持原管理入口，记录这个限制；不要猜测批量导入 CLI。

## 同名技能重复，或更新后又变回旧内容

**可能原因：**CC Switch、Skills CLI、原生插件或项目内技能同时提供了同名项，或者旧更新流程仍在覆盖文件。

**处理：**先备份并确认两个来源的归属。原生插件内技能保留原生管理；普通技能按[接管步骤](cc-switch.md)确认成功后，只保留 CC Switch 为更新/分发入口。不要同时执行 Skills CLI 的同名更新。来源未确定前，不用“全部卸载再装”清理；确认归属后，再在相应管理器内停用多余项，并开新对话复查。

## 管理器显示已启用，智能体却看不到技能或 MCP

**可能原因：**启用的是另一个客户端，客户端尚未重载，当前项目配置有覆盖，或该端不支持工具所需能力。

**处理：**回到 Skills/MCP 列表核对对应的 Codex、DSH 开关；重新打开目标客户端会话，查看其工具/技能发现情况，再按使用卡发起一次明确调用。若仍未发现，在本地检查该客户端的错误和配置范围；公开报告只写脱敏后的原因。不要把管理器有条目写成 `agent-discovered`，也不要删掉 `required_targets` 中失败的一端。

本轮 `grilling`、`grill-me` 已通过原生开关启用到 DSH，哈希一致；优先刷新 DSH 并用短例验证，不再次复制技能。PLC 技能保持 Codex-only，因此在 DSH 不出现不应当作配置故障。

## MCP“连接成功”，回答却没有调用工具

**原因：**CC Switch 的连通性检查只验证 MCP 握手；模型可以在没有工具结果的情况下生成回答。

**处理：**MCP → 该服务菜单 → 测试连接；然后在目标客户端新对话中复制[浏览器或文档检索演示](cc-switch.md)，明确要求使用相应 MCP。检查实际工具调用、输入和返回结果。没有调用就只记录“已连通”；调用报错就记录错误；完整示例成功才是该端 `task-passed`。

如果服务端 SDK 演示已经成功，可以直接从客户端刷新和短例继续。本轮 Playwright 的 25 个工具及导航、截图成功，Context7 的无 key 连接、2 个工具及 Express lookup 成功，均属于服务层证据；`codex mcp get` 识别配置和 DSH YAML 条目存在也不能替代对话内调用。

## 本地 MCP 提示找不到命令、启动失败

**可能原因：**运行环境缺失，命令路径仍指向旧电脑，或者桌面应用还没读到更新后的 `PATH`。

**先检查：**在 PowerShell 执行以下只读命令；它们不会安装依赖。

```powershell
Get-Command node, npm.cmd, npx.cmd -ErrorAction SilentlyContinue | Select-Object Name, Source
node --version
```

**处理：**CC Switch → MCP → 对应服务的编辑入口，核对 `command`、参数和运行方式。已有环境但应用未刷新时，退出后重开 CC Switch 和客户端；路径失效时，按[配置说明](../../configs/README.md)及使用卡填入新机实际路径。Windows 的 npm 命令包装器按配置要求使用 `npm.cmd` 或 `npx.cmd`，不要把完整命令和所有参数塞进 `command` 字段。缺少运行环境则按该工具卡的官方方式补齐；需要 npm 包时使用已记录精确版本及 integrity，不临时换成 `latest`。

检查输出可能含个人路径，留在本地即可。命令缺失时 `node --version` 报错只是这一步的证据，不需要为此修改系统执行策略。

## DSH 连接失败，其他客户端却能用

**可能原因：**各端配置或依赖不同；尤其不能把旧 SSE 配置视为 DSH 的 Streamable HTTP 配置。

**处理：**MCP → 对应服务 → 编辑，核对传输类型、服务方提供的端点以及 DSH 开关。按服务官方支持方式选 stdio 或 Streamable HTTP；不要只把字段从 SSE 改成 HTTP。服务没有兼容端点时，保留 DSH 待解决状态并说明可用的官方替代入口，再单独验证。依据见[官方 DSH 接入说明](https://github.com/farion1231/cc-switch/blob/v4.0.25/docs/deepseek-harness-integration-zh.md)。

## 远程 MCP 返回 401、403、429 或超时

**可能原因：**401 常见于认证缺失或失效；403 可能涉及权限或服务限制；429 可能涉及限流或额度；超时可能来自网络、代理或服务端。具体以服务返回的信息为准，不仅凭状态码认定原因。

**处理：**在本机查看错误摘要；通过服务官方账号入口检查认证、权限和额度，再到 CC Switch → MCP → 对应服务编辑页补齐所需配置。超时先确认该服务官方页面能访问、网络/代理符合原设置；不要为排查一个服务覆盖已有供应商路由。需要凭据但尚未配置的项标为“待配置”，原始认证信息和日志不贴到公开报告。

Context7 在本轮已经无 API key 完成远程工具发现与 Express lookup，因此不能仅因未填 key 就判定当前配置失败。以后若返回认证或额度错误，再依据实际响应处理；此次成功不承诺无 key 长期可用或没有限制。

## 提示词启用后，原来的规则不见了

**可能原因：**启用模板改写了对应客户端的全局规则文件，模板没有包含原有内容。

**处理：**先停止继续启用其他模板。通过[备份恢复流程](migration.md)找回自己的原规则，在本地合并需要新增的内容；再到 CC Switch → 提示词，选择正确客户端后保存/启用合并版本。不要再次用示例覆盖全局 `AGENTS.md`；无法确认备份时先保留当前文件并说明缺口，不凭记忆重建后声称恢复成功。

## 换机后有配置，但插件、技能资源或应用打不开

**原因：**配置备份不保证包含完整运行依赖、插件资源、独立应用数据或可在新机使用的登录状态。

**处理：**按[换机步骤](migration.md)重新登录；原生插件走所属客户端的插件入口，独立应用按使用卡安装；普通技能补齐完整目录，再导入 CC Switch。修正本地 MCP 的旧路径，完成短演示。无需提供真实业务工程，也无需先运行自研 setup/test。

## 旧 `verify.ps1` 退出 2，是安装失败吗

**原因：**旧验证器默认保留 `partial`，不把本地 CLI 检查当成客户端任务通过。也可能有必需的人工步骤未完成；看输出中的具体条目。

如果只想确认旧 profile 内 CLI 的版本及可执行性，可在仓库根目录运行：

```powershell
powershell -NoProfile -File scripts/verify.ps1 -ProfilePath profiles/examples/code-context.json -ToolsOnly
```

该命令即便退出 0，也不验证 CC Switch GUI、MCP 实际调用或换机恢复。它不是“修成全通过”的开关。更多旧命令及影响范围见[旧自动化参考](legacy-automation.md)。

其余已核对来源见[管理指南](cc-switch.md)。网络受限或当前界面与文档不符时，保留查证日期和待核实项；先继续使用已有正常入口，不凭空补参数或“已通过”结果，也不改写管理器数据库。
