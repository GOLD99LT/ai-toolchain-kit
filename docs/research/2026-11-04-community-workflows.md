# 开发者实践与社区反馈：第二轮调研

采样日期：2026-11-04（Asia/Shanghai）。本轮目的不是扩充安装数量，而是比较开发者的实际使用模式，重新评估第一版自建管理逻辑和技能数量。

## 证据口径

- 官方文档和源码用于核对能力、接口与兼容范围。
- 开发者本人发表的文章、仓库配置用于说明“有人这样做”，不推导所有开发者都如此。
- 社区第一人称使用报告用于发现收益和代价；匿名身份、选择偏差与未复测均保留。
- Stars、下载次数、讨论活跃度只作为使用规模线索，不当作满意度或效果证明。
- 调研中的“建议”是针对本用户的判断；“官方宣称”“用户报告”“本机已验证”分别标注。

第一轮的使用规模与具体问题记录继续有效：[采样快照](2026-11-04-adoption-evidence.md)。其中 npm 下载包括依赖、自动化和重复下载；不能用它比较工具实际用户数。

## 1. 实际工作方式样本

| 来源 | 可观察的做法 | 可以借鉴什么 | 不应照搬什么 |
| --- | --- | --- | --- |
| OpenAI Agents SDK 团队的仓库技能实践 [P1] | 从常见任务中提取验收条件、输入输出、命令和检查，再把跨多个工具的重复流程封装成仓库技能 | 从真实任务出发，先让流程稳定，再做技能；用脚本承载可确定执行的检查 | 不能据此先创造一批尚未使用的新技能 |
| Simon Willison 的编码经验 [P2] | 为模型提供合适上下文，以自身技术判断、试验和检查掌握结果 | 需求与上下文清晰、结果可核验；工程知识仍需参与判断 | 不能把熟练开发者的收益推导成所有任务都可无人检查 |
| Armin Ronacher 的 agentic coding 经验 [P3] | 少量参考文件、可操作的工具、稳定的执行环境与反馈 | 项目内记录有效命令和约束，优先调用已有工具 | 文章中的具体模型和当时工具选择有时间背景，不作为本次版本推荐 |
| Peter Steinberger 的开发方式 [P4] | 大量使用可通过帮助信息理解的 CLI，持续迭代；公共技能与项目文件有各自用途 | 先评估现成命令是否足够，再决定是否需要 MCP | 他的个人并行与分支习惯不必成为团队或本用户的默认做法 |
| Claude Code 官方最佳实践 [P5] | 强调验证标准、探索与计划、项目说明、上下文管理、何时用技能或子代理 | 按任务规模选择流程，给智能体可执行的检查方式 | 文档以 Claude Code 为主；不能认为相关 hook/命令在 DSH 中原样适用 |

这些来源支持一项设计判断：工作流复杂度应跟随任务，工具要有明确用途；它们不能证明只存在一种“社区标准工作流”。

## 2. 真实社区讨论与分歧

### Hacker News：技能文件如何管理 [C1]

主题发布于 2026-09-06，采样时官方 API 返回 320 分、299 条评论。这只说明讨论规模。

讨论中同时出现 Git 配置仓库、符号链接、chezmoi、技能分发 CLI、项目专用技能等做法。也有人认为长期维护技能与依赖会占用过多精力，主张保持较少规则；其他用户则指出复杂、多工具流程确实需要可复用说明。

对本项目的推论：应该让“文件归谁管理”清楚，并为不需要某类工具的人保留最小安装方式。不能从这场讨论得出大家都赞成某一个管理器。

### Reddit：按任务复杂度选择工具 [C2]

这是一位用户的使用报告，而非对照实验。作者描述小任务直接交给编码智能体，中等复杂度使用 Superpowers，较大范围使用更明确的文档与规划；评论中也有用户反对过度自动化产生的庞大变更。

对本项目的推论：日常资料整理不强制启动完整开发流程；涉及跨模块代码、迁移或硬件相关变更时，再增加需求、计划和验证步骤。具体框架是否值得安装仍需另查其依赖与适配。

### 关于正面评价的边界

本次找到了具体使用与推荐，但仍不能宣称候选工具“全网一致好评”。报告同时保留负面体验与功能问题，最终依靠本用户的代表性任务验证。

## 3. 对第一版方案的初步修正方向

1. 先比较成熟技能管理工具，避免过早实现自己的复制、升级、冲突和恢复引擎。
2. 先使用本机已有办公能力验证真实任务，再决定是否额外建立 PptxGenJS、MarkItDown 等底层工具流程。
3. 不预先创建四个专用技能。首先用可复用的访谈文档和工作说明；重复使用证明有效后再固化技能。
4. 不默认安装多个开发流程框架。保留现有 Superpowers，其他框架作为有明确触发条件的候选。
5. 将跨智能体共享分为内容/规则共享、普通技能共享、特定工具运行验证；宿主专属插件另行管理。
6. 将可恢复目标定义为“可说明的配置与可验证的能力”，同时标明哪些版本可精确固定，哪些只能由原生更新机制管理。

最终取舍、管理工具比较与验证边界以第二版设计为准。
