# AI 工具链工程第二版方案

日期：2026-11-04（Asia/Shanghai）

状态：历史中间稿，尚未实施。独立审阅要求修正；用户补充了以 Understand-Anything 为例的成熟任务项目发现方向，正在形成第三版。本稿不作为安装授权依据；见 [评审记录](../reviews/2026-11-04-design-v2-review.md)。

## 1. 这次重新设计的结论

推荐建设一个**有使用依据的工具清单、可复用的访谈入口，以及调用成熟工具的部署指南与少量脚本**。

两个入口仍然保留：本人换电脑时恢复选定配置；别人首次使用时通过工作访谈形成自己的推荐与安装方案。首版验证 Windows、Codex、DeepSeek Harness，优先现有账号和免费/本地能力。

与第一版的实质变化：

| 第一版建议 | 第二版选择 | 调整理由 |
| --- | --- | --- |
| 自建 Skills 复制、冲突、升级和恢复逻辑 | 固定版本的 Vercel Skills CLI 管理独立 Skills | 已有工具覆盖安装与来源解析，工程只负责选择、调用与检查 |
| 首版编写四个自有 Skills | 先提供访谈文档和三个工作说明 | 未经实际任务重复验证，不先固化新技能 |
| 为报告先建立多套运行时 | 先验证已有 Codex 办公能力 | 本机已有插件入口；先找实际缺口，减少重复维护 |
| 将多个工作组合都纳入首批安装 | 基础层先落地，工作工具按验收缺口启用 | 让陌生用户也能选择不同组合，而非复制作者全部环境 |
| 倾向统一客户端实现 | 共享规范、输入与验收标准，允许宿主实现不同 | 技能格式兼容不代表工具、插件或运行时等价 |
| 笼统记录“可恢复” | 明确精确固定、宿主管理、人工恢复三类 | 原生插件、账号与 GUI 配置不能被一个技能锁文件全部覆盖 |

调研并没有证明一种统一的社区最佳方案。开发者的第一手实践与用户反馈支持的是：保持基础规则简洁、为任务提供反馈、按复杂度选择流程、对有价值的重复工作做封装。详见 [社区实践](../research/2026-11-04-community-workflows.md)。

## 2. 推荐的日常工作方式

### 轻任务：直接做，并检查结果

适用：整理一次测试记录、改一页汇报、补一个表格字段、修复一个局部问题。

给出输入、目标和验收条件 → 使用现有能力 → 检查输出 → 保存来源和结果。不强制生成完整 PRD、设计文档或多代理任务树。

### 复杂开发：计划、实现、运行验证、评审

适用：跨模块需求、Keil → GCC 迁移、影响硬件行为的代码更改。

继续使用已有 Superpowers：明确需求与影响范围 → 小范围计划 → 分步实现 → 执行构建/测试 → 审查差异 → 记录结论。每一步的结果应能对应需求，而不是仅增加 Markdown 文件数量。

长期迁移可以记录“当前目标、完成情况、下一步、验证结果”。只有持续使用后确认不足，才在该项目试用 OpenSpec 等规范工具。GSD、spec-kit、ECC 不作为全局默认套装，也不让两套流程同时主导同一个变更。

### 日常管理：按清单更新，按任务启用

工具更新由用户或智能体按需发起。先查看来源、版本变化与当前任务需要，再修改选择记录并验证。保持固定来源的 Skills 不使用无差别 `update all` 作为恢复流程。

不增加定时巡检、自动推送或持续监控；这些不是当前确认的范围。

## 3. 全局管理：复用现有工具，明确文件归属

| 管理内容 | 负责方 | 工程承担的工作 |
| --- | --- | --- |
| 共享的独立 Skills | 固定版本 Skills CLI | 保存完整来源、版本、选择和验证结果；调用原生安装命令 |
| Codex 原生插件及其内部 Skills | Codex 插件管理器 | 记录插件来源与恢复步骤，不再导入副本 |
| 供应商与 MCP | CC Switch 已支持的客户端配置接口 | 提供不含密钥的模板和依赖清单，核查实际生效 |
| DSH 特有插件和能力 | DSH 原生机制 | 记录依赖与差异；没有官方接口时使用明确的手工步骤 |
| 项目规则、报告结构、访谈与验收文档 | Git 仓库 | 提供可审阅历史和可分享示例 |
| 用户凭据、公司资料和实际业务模板 | 原生应用或本机私有位置 | 公共工程仅记录如何提供输入，不收录实际内容 |

CC Switch 保留独立的技能源目录，不导入、同步或更新由 Skills CLI 负责的同名技能。Skills CLI 也不处理 Superpowers 原生插件缓存。任何其他管理器都不再同时写这些目录。

chezmoi、mise、rulesync 都值得了解，但暂不新增：当前需要管理的配置和运行时还不多。出现大量 dotfiles、多版本运行时冲突或多宿主规则转换需求时，再分别引入对应工具。

## 4. Skills 部署与恢复的具体方式

### 4.1 首选实现

- 以 `skills@1.7.6` 作为本次核查过的实现候选；npm 元数据和对应源码已读取。该版本要求 Node.js >=22.20.0，本机 v24.15.0 满足。
- 同时固定 CLI 版本和技能上游完整 40 位 commit SHA，使用受支持的 GitHub tree 来源格式；不把移动分支或未经验证的 `owner/repo@tag` 写法作为确定版本保证。
- 显式选择技能和作用范围，不使用“全部技能、全部智能体”安装模式。
- 普通跨项目技能安装到用户级共享目录，项目特定技能安装在项目范围。Windows 优先采用该 CLI 支持的 `--copy` 模式，不把绝对路径 junction 当作 Git 资产。
- 默认由 CLI 的 Codex 目标写入共享目录。该版本没有 DSH 专用目标，不使用虚构的 `--agent dsh`。

### 4.2 DSH 如何读取

已核查与本机登记版本一致的 DSH tag `dsh-v0.2.1-rc.5`：filesystem Skill 插件支持项目与用户级 `.agents/skills`。

实施前需检查插件是否启用、来源是否关闭、`DSH_AGENTS_HOME` 是否改变，以及 `.dsh/skills` 是否有更高优先级的同名内容。安装后必须在两个客户端分别验证发现和实际调用。

这条路径解决的是普通技能的发现机制；Codex 专属工具名、子代理调用或插件运行时不会因此自动变成 DSH 能力。

### 4.3 不依赖实验性恢复作为核心

`skills-lock.json` 与 `experimental_install --frozen-lockfile` 有适用范围和实验性限制，首版不用它们承诺全机恢复。恢复以工程中记录的明确来源逐项调用受支持的安装命令，并核查内容。

固定版本安装若失败，停止该项并报告，不静默回退到 HEAD/latest。若发现本地同名内容与预期不同，先保留原件并输出差异，不无条件重装。

安装计划必须先列出现有项的归属。已由另一管理器维护、来源不明或包含本地修改的同名项，不直接交给安装命令覆盖。对已安装且来源/内容符合记录的项跳过；不相符的项停止并报告。这里只做安装前的条件检查，不实现另一套自动同步与冲突合并机制。

技能的依赖也要列入计划：被引用的其他技能、CLI、MCP、运行时以及宿主专属工具都分别核查。一个目录能被发现，不等于依赖闭合。例如上游 `grill-with-docs` 入口会调用 `grilling` 和 `domain-modeling`，不能只安装入口文件就宣布可用。

### 4.4 现有 grill-me/grilling 的处理

现有本地版本先保留。它们的文件来源、调用方式与上游版本要先核对，再决定是否迁入统一管理。

本人换机需要的本地修改保存在私有源文件集合中，公共工程只引用可公开的上游与通用示例。恢复报告应明确：需要提供私有源文件，还是可以从固定上游重建。不能把本机文件存在当成公开仓库已经可恢复。

## 5. 工具选择：基础、触发新增、暂缓

### 基础层

| 项目 | 首版动作 | 依据 |
| --- | --- | --- |
| Codex、DSH | 保留已有安装并检查版本、技能发现与可用工具 | 用户已在使用，避免不必要的宿主迁移 |
| CC Switch | 备份并检查现有配置后，升级至已核查的 v4.0.25，再验证 Codex/DSH 供应商与 MCP | v4.0.25 发布源码已包含 DSH；本机 4.0.18 没有原生 DSH 接入 |
| Skills CLI | 使用固定版本，作为共享独立 Skills 的安装入口 | 官方安装能力可替代自建文件分发逻辑 |
| Superpowers、grill-me/grilling | 保留、去重并记录来源 | 已能覆盖开发流程和需求访谈，不默认叠加另一整套框架 |
| Codex 已有办公能力 | 作为报告、PPT、BOM 的首轮执行路径 | 现有能力先经任务检验，再决定缺少什么 |

现有办公能力的可恢复来源必须单独核对：记录插件/包标识、当前版本或宿主管理方式、获得途径和依赖。若新电脑无法通过支持的方式获得相同能力，应在恢复报告中列为缺口并选择可验证的替代方案；不复制 Codex 私有运行时，也不因本会话可用就承诺其他安装环境同样可用。

CC Switch 的 Tauri 内部函数不作为对外稳定 CLI。支持官方接口的步骤自动化，其他步骤生成明确的原生 UI 指引；不写其内部数据库。

### 只有出现相应缺口才新增

| 任务缺口 | 首选候选 | 启用前验证 |
| --- | --- | --- |
| 普通网页阅读无法完成动态交互或登录后的任务 | Playwright CLI；agent-browser 为替代；需要持续 MCP 工具会话时再比较 Playwright MCP | 用同一网页任务验证；不同时装多个浏览器入口 |
| 当前能力无法稳定处理输入文件 | MarkItDown 等格式读取工具 | 用实际格式验证；隐藏页、表格和来源完整性需要核对 |
| 需要可独立重建的固定 Markdown → PDF 输出 | Pandoc + Typst | 中文字体、表格、长段落与分页样例通过 |
| 当前 PPT 能力不能满足所需可编辑布局 | PptxGenJS 等底层实现 | 用公司模板副本验证，实际打开检查；不只看文件是否生成 |
| 软件库/API 文档经常过时或难以定位 | Context7 | 查到目标库/版本，明确服务依赖；不假设覆盖全部 STM32/EDA 文档 |
| 长期迁移确实需要规范文件追踪 | 单项目试用 OpenSpec | 与当前任务流程分工清楚，不全局强制、不与其他规范框架重复主导 |

现成技能中，Matt Pocock 的 `grill-with-docs` 与“访谈时沉淀决策”需求相近，可作为当前入口的替代候选；其 `grilling`/`domain-modeling` 依赖和宿主调用方式必须先验证。它不是与现有 grilling 同时强制运行的新流程。

“按需”不等于无限延期：阶段验收中一旦某能力失败，就给出有依据的单项修复方案并再次验证；仍失败则标明未完成。

### 明确暂缓

- 预先编写四个专用 Skills，以及自建包管理器、完整 GUI、完整状态同步引擎。
- 默认整包叠装 GSD、BMAD、ECC、spec-kit、多个浏览器管理器或自动学习/记忆系统。
- 因仓库公开就将 Anthropic source-available 办公技能或宿主专属运行时搬进公共工程。
- 将嘉立创 EDA 旧客户端直接当作已有官方 CLI/MCP 的版本使用。官方要求 V4.1.60+，本机登记 2.2.39.2；升级与设计文件验证另行安排。

## 6. 三类工作如何落地

### 管理、测试与汇报

先建立通用内容约定：资料来源、项目/测试标识、日期、结论、问题、下一步。资料命名与归档先输出预览；对真实文件的移动/重命名按明确任务执行。

Markdown 作为可审阅内容源，PDF 作为交付输出。PPT 的公司版式与个人汇报结构分别管理。第一轮使用合成或脱敏资料验证，再接公司模板；格式生成成功不等于业务内容正确。

不预先引入项目管理 SaaS、数据库或新的办公平台。

### STM32、嘉立创 EDA 与手工 BOM

保留 Keil + CubeMX 的现有流程。为代码变更保留需求、差异、构建命令和日志；实际编译要有指定工程，硬件结果单独记录。

手工 BOM 先明确料号、规格、封装、数量、单位和合并规则。使用现有表格能力输出差异、缺失项和重复项，原件与报告分开。列映射必须从实际样例确认。

GCC + VS Code 修复、PCB 实时修改、嘉立创升级、烧录和在线调试都需要明确对象后单独执行；工具链基建不自动实施这些业务变更。

### 信息搜集与个人技术实践

按需搜集 → 核对原始来源与日期 → 记录条件和限制 → 比较候选 → 输出可行动方案。先使用宿主已有搜索与阅读能力，任务不足时才增加浏览器工具。

来源记录应区分作者宣传、实际用户体验和本机验证；筛选工具时不以 Stars 或 npm 下载量推导整体口碑。X 是否可访问、是否需正常登录，以实际任务检查为准。

## 7. 两个可复用入口

### A. 本人换机恢复

1. 获取工程的确定版本，选择已有的个人组合。
2. 检查宿主、Node、Git、路径与技能冲突。
3. 显示要执行的原生安装命令、固定来源及人工步骤。
4. 调用受支持的安装方式；恢复原生插件；按需提供私有技能/模板；正常登录原有账号。
5. 分别检查两端能力，输出哪些已通过、哪些需要人工操作、哪些仍不支持。

### B. 别人首次使用

1. 在已有智能体中读取通用访谈入口，确认任务、系统、客户端、预算和自动操作范围。
2. 查阅候选清单及证据；工作不在现有覆盖范围时继续调研，不能强套作者的三个工作组合。
3. 保存个人选择和理由，生成可审查的安装方案。
4. 确认方案后进入同一套安装与验证流程。

访谈入口首先是普通 Markdown 提示文档，不要求用户先装新 Skill 或额外购买服务。它保留“发现需求—解释推荐—确认方案—安装验证”的完整步骤，使用稳定后再决定是否封装成 Skill。

## 8. 最小工程结构

```text
README.md                       两个入口、支持范围、当前验证状态
AGENTS.md                       简明工作约定与有效检查方式
catalog/
  tools.json                    工具、用途、证据、适用条件
  sources.lock.json             CLI 版本、不可变来源与验证记录
profiles/
  examples/                     可公开的选择示例
prompts/
  onboarding.md                 可在不同智能体中使用的访谈入口
playbooks/
  reporting.md                  报告内容与验收约定
  embedded.md                   构建、BOM 和硬件结果约定
  research.md                   来源核实与行动方案约定
scripts/
  doctor.ps1                    只读检查已有版本、路径与冲突
  setup.ps1                     调用成熟工具；不另写文件分发引擎
  verify.ps1                    验证来源、发现结果和样例能力
docs/
  requirements/ research/ design/ reviews/ guides/
examples/                       合成输入与预期结果
.local/                         私有选择、源文件、输出、备份；不提交
```

按实际功能创建目录，保留已经完成的研究历史。脚本只做参数、调用和检查；不再建设一套通用安装数据库、事务引擎或跨应用内部配置编辑器。

数据约定控制在三个文件类别：

- `tools.json`：ID、用途、上游、证据及日期、已知限制、依赖、安装/验证方式。
- `sources.lock.json`：所选工具/技能的来源类型、精确版本或完整提交、技能名、受管范围、负责方、内容校验记录。宿主管理的插件明确标记为宿主管理，不能填假固定版本。
- 个人选择：选中的能力、目标客户端、必要/可选标记，以及私有源文件的相对引用。个人路径解析在本机完成，缺失私有源文件明确报告。

源文件内容未验证前，锁定记录只能标为候选；不能用空校验值或“latest”代表已锁定。来源、依赖或校验缺失的条目不进入无人干预的安装步骤。

用户本机路径用参数或环境解析。个人组合留在私有位置，需要换机时由用户携带；公共仓库提供可复用的示例和生成方式。账号、公司模板和历史会话不在公共仓库范围。

## 9. 恢复与验证等级

| 类别 | 能承诺的范围 | 必须核查 |
| --- | --- | --- |
| 固定来源的普通 Skills、CLI 包 | 记录明确版本/提交并校验内容 | 实际安装内容与期望相同；来源无法取得时不回退最新 |
| 原生插件与桌面应用 | 记录已验证版本、来源和官方恢复方式 | 原生自动更新策略可能改变版本，恢复后重新验证 |
| 账号与应用内配置 | 提供正常登录、导入或设置步骤 | “生成了模板”不是“已经生效” |
| 私有技能/模板 | 使用个人携带的私有源集合 | 缺失时明确报告，不能从公共示例假装恢复 |

每项结果区分：文档支持、文件已安装、客户端已发现、代表性任务通过、需要人工操作、未通过/不支持。只要某必需能力尚未通过，就不宣称双智能体完整可用。

第二台电脑不可用时，只能报告隔离目录中的恢复演练，不称为实机换机成功。

## 10. 实施阶段与验收

### 阶段一：基础层和双入口

完成工具目录、访谈入口、示例选择、只读诊断与薄脚本；固定 Skills CLI 版本并检查既有技能归属。备份并升级 CC Switch，验证新版本对现有配置和 DSH 的行为。

此阶段只安装有明确作用的基础管理能力。使用一个简单技能样例验证固定来源安装、重复执行、同名冲突、发现和调用；不以复制大量技能作为验收。

### 阶段二：工作样例与按需补齐

分别验证 Markdown/PDF、公司格式 PPT（先合成模板）、BOM、按需研究。记录每种宿主已具备的能力和缺口。

出现缺口时，按本方案的单项候选顺序试用并验证。DSH 可以使用不同实现达到相同验收标准；若尚不能完成，要在能力矩阵中明确体现，不能用 Codex 的成功替代 DSH 的结果。

每个样例至少记录输入、输出、人工操作次数、发现的错误及返工原因，并与用户当前做法作同条件比较。能生成文件但增加大量返工的方案不作为默认推荐；不预先宣称节省某个百分比。真实公司模板和 BOM 尚未提供时，报告只能称合成样例通过。

### 阶段三：恢复演练与分享

用隔离路径测试：固定来源安装、原文件保留、重复执行、错误来源、同名覆盖、缺少私有文件和必要人工步骤。不会为模拟新电脑而改动全局 HOME 或清空真实客户端配置。

整理使用说明、更新与排错指南、原创内容和第三方来源说明。本地结果可审阅后再确定 Git 平台、仓库名和公开范围，并执行用户授权的发布。

## 11. 当前证据与待验证条件

已核查：用户需求、现有安装线索、实际 Node 版本、Skills CLI 固定版本源码与元数据、DSH 对应 tag 的共享目录契约、CC Switch 发布版本的 DSH 接入，以及社区实践与具体使用报告。

尚未执行：技能安装、CC Switch 升级、双端任务、公司模板、真实 BOM、实际工程构建或换机恢复。它们属于批准方案后的验收工作。

首版不依赖以下未证实前提：完整复制 Codex 内部运行时、CC Switch 对外稳定批量 CLI、`--agent dsh`、实验性锁文件恢复覆盖整台机器、所有原生插件都能固定历史版本。
