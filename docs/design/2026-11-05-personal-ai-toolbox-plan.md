# 个人 AI 工具箱方案：选型、现成管理、安装与使用交付

日期：2026-11-05（Asia/Shanghai）

状态：用户于 2026-11-05 明确批准按本方案调整文档、配置目录并全面推进。设计形成时的讨论边界保留在下文；当前实际安装、同步与未验证状态以 [执行记录](../validation/2026-11-05-toolbox-rollout.md) 为准。见 [方案评审](../reviews/2026-11-05-personal-ai-toolbox-plan-review.md)。

## 1. 最终要交付什么

帮助用户根据自己的工作和电脑环境，找到成熟、实用的 AI 工具、Skills、插件和开源项目；解释选择，协助安装与配置，用现成软件尽量统一管理，并教会用户日常使用。

Git 仓库保存这套可复用的选择过程、使用手册、安装来源和迁移说明。本人换电脑可以恢复工具箱，其他人可以经过访谈得到适合自己的组合。

完成标准是用户知道“这项工作该用谁、从哪里打开、给什么输入、结果怎么看、如何更新或停用”。当前项目不以替用户执行全部工作、开发管理软件或自动接管业务项目为交付目标。

## 2. 对历次沟通的重新归纳

| 已确认的需求 | 本版对应做法 |
| --- | --- |
| 找高使用、有好评且适合自己的工具 | 官方能力 + 社区具体经验 + 维护情况 + 用户任务匹配；不按 Stars 单一排名 |
| 类型不限于 Skill | 同时比较客户端、插件、MCP、CLI、完整应用和成熟项目模板 |
| 先了解工作特点 | 已确认的三类工作直接沿用，不再重复访谈 |
| 安装或指导安装 | 使用产品官方入口或成熟管理器，明确已装/待配/可选 |
| 尽量全局统一管理、兼顾 Codex 与 DSH | 现成管理器优先；普通技能与 MCP 逐客户端确认，专属插件单独说明 |
| 解释怎么使用 | 每项提供中文使用卡和一个短演示，用户能独立复用 |
| 换机、分享给别人 | 本人按清单和官方恢复方式迁移；新人按问答重新选择 |
| 工程文件有规划、能放 Git | 人能看懂的指南和来源记录为主；沿用现有目录，不增加自研管理层 |
| Understand-Anything 只是例子 | 保留它作为代码阅读候选，不把举例当作立即运行整个业务工程的命令 |
| 写完先严格评审 | 本稿先做作者自查，再用独立上下文检查目标、可用性和过度设计 |

三类工作：

- **管理与汇报**：手工归档项目/测试资料，AI 汇总 Markdown 后转 PDF，有公司 PPT 格式，尚未形成个人汇报内容模板。
- **嵌入式与硬件**：Keil + CubeMX，GCC + VS Code 尚在搭建；嘉立创 EDA；BOM 手工维护。
- **信息和个人实践**：按需从 X/网站找信息，整理可行动方案；有兴趣做小网站和 VPS 实践。

之前的偏差是把换机复用做成自建安装框架，把效果验证扩大为业务项目分析，工具教学反而不足。此前执行和测试记录继续真实保留，但不能作为继续扩大开发的理由。

## 3. 全局管理：推荐先用 CC Switch

**推荐选择：以已经安装的 CC Switch 作为日常配置主入口。** 官方 v4.0.25 文档列出供应商、MCP、普通 Skills、提示词及受支持客户端管理；DSH 专门文档也说明相关接入。[S1][S2]

这次明确改变旧设计：不再要求用户主要通过本仓库的 setup/verify 脚本或 Skills CLI 管理普通技能。现成图形界面能完成的操作，优先在图形界面完成。

| 内容 | 用户主要从哪里管理 | 需要说明的边界 |
| --- | --- | --- |
| 已有供应商配置、模型连接 | CC Switch 对应客户端页面 | 保留现有可用连接；不为整理工具箱自动改供应商或路由 |
| MCP | CC Switch 的 MCP 页面 | 配置和连通后，还要在所选客户端调用一次；进程连接不等于任务成功 |
| 普通独立 Skills | CC Switch 的 Skills 页面 | 先确认原来源和文件归属，再导入/安装；不重复导入原生插件内部技能 |
| 全局提示词 | CC Switch 的提示词功能 | 先保留用户已有内容，再协商合并；不直接覆盖 AGENTS.md 等全局约定 |
| Superpowers、Codex 原生办公插件 | 各客户端原生插件入口 | 不能以复制插件里的 SKILL.md 代替完整插件安装 |
| Understand-Anything 等完整项目 | 项目官方安装方式与自带界面 | 依赖、技能文件归属和客户端支持单独登记 |
| Presenton 等独立应用 | 软件自己的入口 | 在工具箱手册中集中导航，不承诺 CC Switch 能控制独立应用全部功能 |

普通 Skills 若由 CC Switch 接管，同一份内容不再同时由 Skills CLI 更新。迁移前备份并核查；复杂产品或原生插件保持自己的管理者，不为统一外观破坏其依赖。

### 现成方案的取舍

- **CC Switch 为主，原生入口补充：推荐。** 与用户已有环境、希望有图形管理入口的目标最接近。
- **仅用客户端各自入口：备选。** 管理器遇到实际兼容问题时，可暂用对应原生方式；在手册中明确差异。
- **CC Switch + 多个同步/版本管理器：暂不采用。** 只有出现明确的多机规则同步或多运行时问题，才重新评估 rulesync、chezmoi、mise 等。

“统一管理”在这里是让主要操作有固定入口，所有工具的状态和用法有一份清单。它不承诺独立软件、宿主专属插件、账号和会话能全部互相替换。

## 4. 为你配置的工具组合

下表是选择方案，不是本轮安装清单。已有状态来自本机盘点与执行记录；候选功能来自已归档调研和本次官方核对。

### A. 已有能力：先整理并教会使用

| 组件 | 当前事实 | 该怎样交付给你 |
| --- | --- | --- |
| Codex + DeepSeek Harness | 已有两端 | 说明每端现有模型、能做的任务和可用工具；不另换一套客户端 |
| CC Switch | 已升级到 4.0.25 | 完成当前配置与管理归属整理，给出主要页面的操作指南 |
| Superpowers | Codex 已有插件 | 解释何时用于复杂开发，怎样请求需求分析、调试、评审；轻任务不强制跑完整流程 |
| grill-me / grilling | 本地已有 | 作为需求澄清工具教用；现有版本不是自动等同于上游整包，不重复安装 |
| 文档、PDF、表格、演示能力 | Codex 会话已有技能入口 | 给出测试汇总、MD/PDF、公司 PPT、BOM 的示例请求；来源可恢复性另做说明 |
| Repomix 1.18.1 | 项目内已装，合成材料保留试验通过 | 作为需要整理代码上下文时的辅助；记录可复制的启动方式，不要求全局 MCP 常驻 |

这些能力需要补的是“从哪里调用、怎么输入、怎样看结果”，不是重新编写同类技能。

### B. 推荐优先补充：浏览器操作与软件文档查询

| 候选 | 对你的价值 | 使用方式与条件 | 本版建议 |
| --- | --- | --- | --- |
| **Playwright MCP** | 在需要交互的网页中查看信息，或检查个人网站页面 | 通过所选智能体调用浏览器工具；CC Switch 管配置。它不是搜索引擎，X 登录/可访问性需实际确认 | 优先检查是否已有同等能力；缺少时作为第一项新增，完成双端短演示 [S4] |
| **Context7 MCP** | 写小网站或接软件库时查对应版本文档 | 智能体通过工具检索；需要外部服务，账号/额度按实际配置核对，不能假设涵盖所有 STM32/EDA 文档 | 作为第二项新增候选；确认现有账号/额度条件后配置，未满足则保持可选 [S5] |

选择 MCP 入口是为了配合当前的集中管理与多智能体使用需求，不宣称 MCP 在所有场景都比 CLI 好。若现有浏览器能力已满足需要，或实际兼容更适合 CLI，则用现成替代入口并在使用卡说明；同类功能不同时叠装多套。

### C. 专业能力：保留具体推荐，按需要选择

| 需求 | 优先了解的现成项目 | 推荐条件与使用入口 |
| --- | --- | --- |
| 看代码整体结构和功能关系 | **Understand-Anything** | 有图谱、导览与解释入口，先展示官方演示并解释操作；选择后按官方方式安装，Codex 路线已有文档，DSH 不预设等价 [S6] |
| 长期做 C/C++ 定义与引用导航 | **Serena** | 编译参数/语言服务器条件满足时采用；不把修复整个 GCC 环境变成安装工具箱的前置要求 |
| 扫描测试资料、复杂 PDF 表格难读 | **Docling** | 确有这类输入时增加读取能力，普通文本继续用现有办公工具 |
| 希望有可视化的 PPT 制稿界面 | **Presenton** | 提供生成和编辑产品流程；模型条件、公司格式及导出效果需解释和短演示，不承诺母版无损导入 [S7] |
| 做个人介绍站、博客 | **AstroWind 等成熟模板** | 有具体站点需求时给出适配模板，用现有智能体修改；模板属于项目材料，不必现在全局安装 |
| 重复批量整理网站资料 | **Crawl4AI / Firecrawl** | 与偶尔搜索不同；采集量与维护/服务成本成立后再选一个 |
| 维护多个 VPS 服务 | **Coolify / Dokploy** | 先作为部署管理候选；安装在目标服务器，不因本次工具箱配置就启动部署 |

这部分沿用 [任务型项目目录](../research/2026-11-04-task-project-catalog.md) 的用途、维护、许可和用户问题说明。不因某候选暂未安装就删除它，也不以“工具越少越好”排除确实有帮助的完整产品。

## 5. 每项工具必须配一张中文使用卡

使用卡是核心交付，内容固定为：

1. **一句话用途**：替你解决哪一类具体问题。
2. **何时用、何时不用**：与已有能力有什么区别。
3. **从哪里打开**：应用页面、智能体、菜单或一条经核查的命令。
4. **先准备什么**：文件、网页、账号、模型、运行环境。
5. **两个可复制例子**：尽量贴近你的工作。
6. **会得到什么**：对话、文件、图、网页或编辑界面，结果存在哪里。
7. **如何自己判断能用**：一次小演示和明显的成功/失败信号。
8. **如何管理**：安装负责人、更新、停用/卸载及一个常见故障的处理方式。
9. **费用与数据处理**：免费代码与模型/API费用分开；哪些内容会交给配置的模型或服务。

### 使用卡样例：Playwright MCP（拟配置，尚未实测）

- **用途**：让当前智能体操作网页，适合动态页面阅读与自己网站的页面检查。
- **入口**：配置完成后，在支持的智能体对话里提出网页任务；无需先打开自研工具箱程序。
- **示例一**：使用已配置的浏览器工具，打开我给的三个产品页面，对比 CAN 通道数量、接口和供电范围；缺失参数标注未知，并附原页面来源。
- **示例二**：打开我的本地网页，检查导航能否点击、手机宽度下有无溢出；先报告问题，不修改代码。
- **成功信号**：浏览器工具确实被调用、页面打开、结果引用可核对。无法登录或页面未打开时明确失败，不凭网页标题补全内容。
- **管理位置**：CC Switch 的 MCP 页面；需要更新包时按记录的安装来源操作。实际菜单与参数以配置时的版本为准。[S1][S4]

这些是教学示例，不是在本轮替用户执行对应业务任务。

## 6. 安装与教学的交付顺序

### 第一步：对齐清单和管理入口

利用已有盘点，形成“已装可用、已装待配置、建议新增、按需备选”四类清单。优先确认 CC Switch 中 Codex/DSH、Skills 和 MCP 的管理路径，以及现有原生插件归属。

输出：一页个人工具箱总览和现成管理器使用指南。此时用户应能回答“在哪里查看和开关我的工具”。

### 第二步：配置核心工具并完成短演示

在方案确认后的安装阶段，整理已有技能与办公能力；对选中的浏览器/文档检索能力完成官方方式安装或连接。每项配置后就给使用卡和一个短演示，再处理下一项。

演示优先采用公开页面、简单文件或官方样例。普通工具不用完整业务工程、虚拟机或对照实验作为前置条件；遇到确有环境风险的复杂安装，再采用该工具相称的备份或隔离方式。

### 第三步：有明确新增价值时，再补充专业项目

在代码阅读、PPT 界面、复杂资料读取中，若现有能力仍有缺口、明显返工或操作体验可改善，再结合实际需求选择一个专业工具；没有明确增益则跳过这一步。Understand-Anything 是明确候选，但不是用户已经选定必须安装的项目，不以“再装一个”作为项目完成条件。

完成“看得见入口、能打开、示例成功、知道如何再次使用”即可交付配置阶段。完整项目框架分析、真实公司汇报、PCB 修改或 VPS 部署属于后来明确发起的工作，不自动接续。

### 第四步：保存换机与复用资料

本人换机优先采用现成管理器支持的备份/恢复及各产品官方安装方式，按清单补齐原生插件和独立应用，正常重新登录。恢复目标是相同选择与可用功能；只有确有必要的项目才固定具体历史版本，不承诺整机逐字节复制。

CC Switch 的配置、登录数据和备份可能包含私密信息。它们保留在个人私有位置；公开 Git 仅存无密钥的清单、模板、来源及说明。官方云同步若需要新增存储账号，列为可选，不作为首次使用的前提。[S1]

他人首次使用：阅读项目说明 → 把通用问答交给自己的 AI → 形成自己的工作画像和推荐 → 选择后安装/配置 → 领取对应使用卡。新人不需要先学本仓库 JSON schema 或运行自研安装器。

## 7. 仓库定位与目录收敛

仓库定位为 **AI 工具选型与使用手册，以及可复用的配置参考**。保留开源工程的条理，但把读者入口放在“我该用什么”和“怎么用”。

后续确认后，优先调整已有目录，不为了新方案再建一套平行结构：

```text
README.md                  工具箱总览、首次选择、本人换机两个入口
catalog/README.md          候选推荐、取舍与适用条件
recipes/                   各工具中文使用卡，沿用已有文件
prompts/onboarding.md       新人工作需求访谈入口
playbooks/                 报告、嵌入式、信息研究的使用组合示例
docs/guides/               CC Switch 管理指南、换机与常见问题
docs/research/             来源、维护、社区反馈与采样日期
docs/design/               方案与历史调整
docs/validation/           实际已配置/未验证的简明记录
.local/                    本人私有配置、备份和输出，不进公开 Git
```

现有 catalog JSON、runtime、scripts、tests 暂留，不删除、不要求继续维护成产品。它们从默认使用流程退为已有技术材料；确认后再决定哪些保留为辅助，哪些归档。用户不需要通过运行测试来开始使用工具。

若普通 Skills 交给 CC Switch，旧脚本/CLI 不再被教作同一份技能的日常管理入口。已装 Skills CLI 与 Repomix 暂不卸载，避免为修订方案再次扰动环境。

公开仓库已经存在。这轮新方案只在本地审阅；确认内容后再整理和发布文档，不自动改变当前公开版本的承诺。

## 9. 验收标准与下一步

一个工具进入“已交付”必须同时满足：

- 用户知道为什么给自己选它，也知道主要限制。
- 已安装或已接入；需要账号或环境而未完成的项明确标注。
- 在约定客户端完成一次短演示，或独立应用完成一次基本操作。
- 用户有可复制的例子，知道结果在哪里。
- 知道如何更新、停用、卸载，谁负责管理。
- 换机时知道从哪里取得工具和如何恢复必要配置。

同一工具只在 Codex 实际演示通过时，不写 DSH 也通过。若用户要求两端都有而有一端不支持，要解释并给现成替代，不静默减少需求。

**本版建议的下一步是整理 CC Switch 与现有工具、完成第一批使用卡，再讨论选定的新增项。** 不继续分析交接 ZIP，不再先构造新的测试平台，也不要求用户再回答已经确认的工作画像。
