# AI 工具链工程首版设计

日期：2026-11-04（Asia/Shanghai）

状态：历史方案，未实施。当前入口为 [第三版方案](2026-11-04-ai-toolchain-design-v3.md)，本文件保留作比较，不作为安装依据。

## 1. 交付目标

建设一个可公开分享的 AI 工具链工程，提供两个入口：

1. **恢复我的环境**：读取已保存的工具组合与版本，检查新电脑，展示将执行的操作，再安装并验证。
2. **帮我选择工具**：在现有智能体中访谈工作需求，解释候选工具的作用和取舍，生成个人方案，经确认后进入同一套部署流程。

首版验证 Windows + Codex + DeepSeek Harness。优先已有账号及免费/本地工具；新增付费服务列为可选。使用 CC Switch 承担已核实支持的日常管理。

访谈可以由现有 Codex 或 DeepSeek Harness 执行，工程本身不要求额外购买一个 AI 服务。工具选择的关键依据、采样日期、用户决定和验证结果保存为 Markdown 与结构化配置。

此工程的主体是工具筛选、配置与恢复。管理汇报、嵌入式和信息搜集分别作为可选工作组合，避免把首次交付扩大成多个完整业务系统。

## 2. 方案比较与推荐

| 方案 | 能提供什么 | 主要取舍 |
| --- | --- | --- |
| 文档 + CC Switch 操作指南 | 快速开始、集中日常管理 | 版本记录和换机检查需要更多手工操作 |
| 版本化清单 + 场景组合 + 部署入口 + CC Switch | 同时服务个性化推荐、检查、安装、验证、恢复 | 需要维护少量脚本和客户端适配；推荐 |
| 独立图形管理平台 | 自建完整产品界面 | 增加前端、后台和更新维护，首版收益不足 |

采用第二种。首版提供清楚的 Markdown 文档和 PowerShell 入口，复用已有智能体与 CC Switch 的交互界面。

## 3. 全局管理的职责

| 内容 | 唯一负责安装/更新的一方 | 其他组件如何参与 |
| --- | --- | --- |
| 通用、可移植 Skills | 本工程部署入口 | 使用共享技能目录；CC Switch 不再同步同名技能 |
| Codex 已有原生插件，如 Superpowers | Codex 原生插件管理器 | 工程记录来源、版本和恢复要求，避免重复装一套副本 |
| 智能体专用适配 | 本工程对应的适配器 | 放入该智能体专用目录，记录可用性与差异 |
| 模型供应商、MCP | CC Switch 与各智能体的官方配置接口 | 工程保存不含密钥的模板、依赖和操作清单 |
| 工具运行时与依赖 | 本工程依赖安装步骤 | Node/Python 等分别检查；安装过程采用确定版本 |
| 凭据、会话、本机数据库 | 各原生应用 | 公开仓库不包含这些文件；登录保留明确的人工步骤 |

普通技能优先评估用户级 `~/.agents/skills`，Codex 与 DSH 的官方资料均列出该路径。Windows 首版优先用目录副本与哈希校验，不要求管理员权限来创建链接。

项目级技能可能优先于全局技能，部署前需要报告同名项及来源。DSH 专用目录的同名技能可能覆盖共享目录，因此专用适配默认使用独立名称。未纳管的已有文件不直接覆盖；用户改动过的受管文件先展示冲突。`grill-me` / `grilling` 的现有本地内容先保留并核对来源，不把它们假定为当前上游整包。

环境检查同时核对 CC Switch 当前的技能源目录。采用本分工时，不将工程管理的共享目录设为 CC Switch 技能源，也不通过 CC Switch 或 Skills CLI 导入、更新这些技能。

Codex 专属插件不作“整个插件在 DSH 中完全等价运行”的承诺。跨智能体共享的标准是：技能被发现、引用的工具存在、代表性任务通过验证。

CC Switch 的外部批量导入 CLI 尚未核实。能用官方接口的步骤自动化；其他步骤生成配置和具体的 UI 指引。完成状态区分“已生成”“已注册”“已验证”，不直接改写内部数据库。

## 4. 首批工具清单与用途

下表是待批准的具体首版选择。每项依赖在执行前解析到确定版本并写入锁定清单；正文不把 `latest` 作为恢复版本。

| 工具或能力 | 首版处理 | 对用户工作的价值 | 验收与限制 |
| --- | --- | --- | --- |
| CC Switch v4.0.25 | 在本机配置备份后，从登记的 4.0.18 升级到已核验版本 | 新版本源码包含 DSH 接入，可集中管理 Codex/DSH 的供应商和 MCP | 本机升级、原配置保留、两端连接分别验证；不自动更换供应商 |
| Superpowers | 保留 Codex 已有原生插件，记录恢复方式 | 在代码开发中使用设计、调试和验证流程 | 检查重复技能；DSH 的完整适配不是首版前提 |
| grill-me / grilling | 保留现有能力，核对来源并整理可移植调用方式 | 需求访谈和方案澄清 | 不默认安装整套重复流程技能 |
| Pandoc + Typst | 管理汇报组合的首选 PDF 输出候选，安装后进行样例验证 | 延续 Markdown → PDF，固定报告结构和样式 | 验证中文字体、表格、分页；输出可回查 Markdown |
| MarkItDown | 管理汇报组合按需安装所需格式依赖 | 把现有办公材料转为便于 AI 整理的文本 | 不承担高保真版式还原；需注意隐藏 PPT 页等来源差异 |
| PptxGenJS | 管理汇报组合小规模试装验证 | 生成可编辑的图表、表格和固定汇报布局 | 近期代码推送较少且有特定图表兼容报告；实际打开样例验收，公司模板另验 |
| Playwright CLI + Skills | 信息搜集组合的首选浏览器操作入口 | 按需读取交互网页，验证个人小网站 | 使用固定版本，技能通过统一部署入口纳管；网站登录由用户正常完成 |
| Playwright MCP | 可替代浏览器入口，默认不与 CLI 双装 | 需要持续工具会话或更偏好 MCP 集成时使用 | 若实际双智能体验证表明 MCP 更适合，再记录替换理由 |
| Context7 | 可选，不作为基本安装前提 | 查询软件库/API 的版本相关资料 | 有外部服务依赖；尚未验证 STM32/EDA 特定资料覆盖 |
| Keil 原生命令行 + 轻量工作规则 | 接入现有编译流程 | 需求变更、代码差异、构建日志与检查 | 首版先验证工具定位与调用方式；真实工程构建需指定工程，不默认烧录 |
| 手工 BOM 检查规则与文件脚本 | 嵌入式组合 | 检查缺失字段、重复项及版本差异 | 首版以合成 XLSX/CSV 样例验证；实际列映射待真实文件确认 |
| 嘉立创 EDA 官方 CLI/MCP | 后续可选项 | 直接调用编辑器与扩展 API | 官方要求客户端 V4.1.60+，本机登记 2.2.39.2；升级和真实设计验证单独安排 |
| Vercel Skills CLI | 调研工具候选，首版不作为第二个部署管理器 | 查找其他技能 | 避免与工程或 CC Switch 同时修改同一部署目录 |

浏览器任务先使用按需搜索，不设置 X 定时监控、自动推送或无人值守远程部署。

BOM 检查不会把手工表格假装成可自动同步的设计数据库。先确认字段和比较规则，再输出检查报告；原始文件与报告分开。

## 5. 工程自身需要的少量 Skills

优先复用上述已有工具，只补充与本项目目标直接相关的流程指导：

- `toolchain-advisor`：读取需求记录，按工作场景访谈，解释选择，生成可审阅的组合与安装计划。
- `project-reporting`：组织资料来源、测试结论和汇报结构，调用已验证的文件工具，明确哪些结论缺乏数据。
- `embedded-review`：围绕 Keil/CubeMX 工程与手工 BOM 做影响分析、构建记录和差异检查。
- `research-to-plan`：保留信息来源、日期和条件，比较候选项目，产出可行动方案。

后三项随对应组合启用；不在每个任务中同时加载。技能通过调用命令和读取文件完成工作，尽量避免依赖单一智能体专有工具名。已有办公插件能力若能满足任务，优先调用并记录其依赖；仅复制技能文件不算可迁移实现。

## 6. 数据与版本记录

建议用 JSON 保存机器可读数据，Markdown 保存说明，减少 PowerShell 读取 YAML 所需的额外依赖。

- **工具目录**：工具 ID、用途、上游地址、许可证、来源证据、支持的平台与智能体、依赖、安装/检查方式。
- **工作组合**：选中的工具 ID、可选功能、偏好与需要人工完成的步骤。
- **版本锁定文件**：包版本或提交、下载来源、可获取时的校验值，以及确实完成过的验证。
- **安装状态**：实际路径、版本、文件哈希、归属和当前验证级别，保存在本机私有目录。
- **决策记录**：需求、候选对比、采纳/不采纳理由、日期与证据；不把不可核查的内部推理当作交付。

远端来源无法固定、官方登录或 GUI 步骤必须人工处理时，在恢复报告中明确列出。不能把“重跑最新版本安装命令”称为确定版本恢复。

用户级路径使用环境变量或参数解析。公开配置包含通用示例，个人配置与本机路径放在 `.local/` 等被 Git 忽略的位置。导出恢复配置时只导出可移植字段，不复制整个用户主目录。

## 7. 目录规划

```text
README.md                         项目入口与两个使用流程
AGENTS.md                         仓库工作约定
LICENSE                           本项目原创内容的许可（发布前确定）
toolchain.ps1                     Windows 统一入口
catalog/
  tools.json                      工具目录与来源元数据
  tools.lock.json                 已验证版本与校验记录
profiles/
  base.json                       公共基础
  reporting.json                  管理、测试与汇报
  embedded.json                   STM32、BOM 与硬件资料
  research.json                   按需资料搜集与实践方案
  examples/                       可公开的组合示例
skills/                           本项目原创流程技能
scripts/
  lib/                            检查、下载、备份与校验共用逻辑
  adapters/                       Codex、DSH、CC Switch 适配
templates/                        通用报告、汇报内容结构、配置模板
docs/
  requirements/                   已确认的需求与访谈记录
  research/                       资料、使用证据与兼容性调查
  design/                         设计方案
  decisions/                      实施中重要取舍
  guides/                         安装、使用、更新、迁移与排错
examples/                         合成数据与最小演示
tests/                            必要的部署与恢复测试
.local/                           本机状态、缓存、输出和私有配置；不提交
```

不会把空目录当作交付成果；实现对应功能时再建立目录。当前已有的调研文档保留在上述结构内。

第三方工具默认记录来源并按需获取，不把整个上游仓库或已有插件缓存复制进公开项目。许可证信息与本项目原创内容分开记录。

## 8. 用户操作流程

统一入口拟提供以下动作，名称在实现时固定并写入帮助；目前尚不存在可运行的入口脚本。

1. **检查环境**：列出已装、缺失、版本不匹配、同名技能冲突和手工步骤。
2. **生成方案**：从访谈或已有组合生成安装计划，显示下载来源、版本、目标路径与变更。
3. **应用方案**：只执行选中的已批准步骤；应用原生插件保持原有管理归属。
4. **验证能力**：按工具与智能体分别测试，并输出有证据的结果。
5. **导出恢复配置**：生成不含账号凭据的组合和版本记录。
6. **恢复环境**：读取导出配置，重新检查、预览、应用和验证。

本机已有工具优先复用。二次执行应识别已满足条件的项；文件变更前备份，失败时停止依赖该步骤的操作。恢复仅处理本工程管理的文件与已记录的操作，不能承诺撤销任意第三方安装器或外部账号状态。

## 9. 验收标准

### 工程与恢复

- README 能引导一个新用户选择访谈或恢复入口。
- 访谈结果可以生成不同的工具组合；不把当前用户的工具清单强加给所有人。
- 计划步骤可审查，执行结果与实际文件/版本一致。
- 相同方案重复执行不会增加重复技能或覆盖未纳管文件。
- 在临时目录/隔离用户配置中测试恢复、同名冲突和失败处理，明确这是模拟换机；有第二台实际电脑后再记录实机验证。
- 全部用户路径可配置；公开文件不包含凭据、公司资料、个人绝对路径或运行日志。

### 双智能体

- 在 Codex 与 DSH 中分别验证共享技能被发现。
- 代表性工具调用在两端实际运行；若登录或宿主缺少工具使其未完成，状态明确显示未验证。
- 原生插件与共享技能不会因同名重复安装而同时触发。
- CC Switch 升级后原有配置仍可使用，并能识别 DSH；MCP 注册与连接分别检查。

### 工作样例

- 合成测试数据 → Markdown 报告 → 中文 PDF，检查关键数字、表格和分页。
- 合成汇报数据 → 可编辑 PPT，实际打开检查；公司模板验收在收到模板后单独进行。
- 合成 BOM → 缺失项/重复项/变更报告，不修改原件。
- 指定公开主题 → 带来源与日期的候选比较及行动方案。
- Keil 命令路径、构建参数和日志处理能明确诊断；没有指定实际工程时，不把编译能力标记为通过。

## 10. 执行顺序与暂停边界

用户确认本方案后，按以下顺序实施：

1. 建立最小工程、工具目录、版本记录和环境检查。
2. 实现双入口及共享技能的归属、冲突检查与恢复流程。
3. 备份并升级 CC Switch，注册或指导注册所选 MCP，验证 Codex/DSH。
4. 安装所选工作组合，使用公开/合成样例验证报告、BOM、浏览器能力。
5. 完成使用与恢复文档、必要测试以及本地 Git 审阅。
6. 在本地结果可审阅后，再确定远端平台、仓库名称与公开范围，完成用户授权的发布步骤。

以下工作需要另外明确对象后再执行：修复当前 GCC 工程、升级嘉立创 EDA、修改真实 PCB、烧录硬件、套用公司真实模板、连接或部署 VPS。它们不是本次工具链方案确认后自动执行的动作。

## 11. 审阅时重点确认

建议一次确认：工具组合与可选项、管理分工、CC Switch 升级、目录结构和上述验收范围。公司样例与发布目标可以在对应实施阶段提供，当前无需为这些细节阻塞工程设计。
