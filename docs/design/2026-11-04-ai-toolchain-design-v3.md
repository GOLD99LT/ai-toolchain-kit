# 第三版方案：从工作任务发现并复用成熟项目

日期：2026-11-04（Asia/Shanghai）

状态：已完成作者自查与独立审阅，供用户审核；未安装或运行候选项目。第一、二版保留为历史，本文是新的方案入口。评审过程见 [严格评审记录](../reviews/2026-11-04-design-v3-review.md)。

执行更新：用户于 2026-11-05 批准继续推进；本机已完成的安装、试点与仍未验证事项以 [执行验证报告](../validation/2026-11-05-foundation-and-pilot.md) 为准。上文状态描述设计形成时的阶段。

## 1. 对用户补充思路的评价

这个思路有用，而且应成为本工程的主线：先明确需要完成的工作，再寻找已经解决其中关键环节的成熟项目，评估后直接套用。Skill、MCP、CLI、完整应用、网站模板、可部署服务都可以成为候选。

Understand-Anything 是有效的例子：它把代码分析、可视化和导览组合成一个完整项目，提供的价值比“再写一段读代码提示词”更具体。它同时也说明需要认真评估：支持 C/C++、有 Windows 安装器，并不能直接推出 Keil 工程的中断关系分析正确或 DSH 原生接入已可用。

因此选择顺序是：

**任务与当前做法 → 成熟项目发现 → 证据和适配评估 → 小范围试点 → 记录结果 → 纳入可恢复工具组合。**

高 Stars 用于发现候选，维护与发布用于判断状态，实际用户报告帮助发现限制，最后由代表性任务决定是否提效。没有充分证据时，标为候选而非“成熟可用”。

第二版偏重环境管理和减少工具，对任务型项目挖掘不足。第三版修正这一点，同时保留其明确管理归属、复用现成安装方式的优点。

## 2. 已确认需求与范围

- 两个入口：本人换机恢复；别人首次使用时访谈、研究并生成自己的工具方案。
- 首版环境：Windows + Codex + DeepSeek Harness，CC Switch 作为集中配置候选。
- 账号与费用：优先现有账号及免费/本地能力；新增付费服务明确列为可选，不假定聊天订阅包含第三方 API。
- 工作：项目/测试资料整理、Markdown → PDF、公司格式 PPT；Keil + CubeMX 的 STM32 开发、未来 GCC + VS Code、嘉立创 EDA、手工 BOM；按需网站研究与个人小项目。
- 本轮只有调研、设计与评审。Understand-Anything 是用户给的案例，不是已授权安装的指定项目。

## 3. 任务型项目清单与套用建议

完整版本、许可、使用证据及问题链接见 [任务型项目目录](../research/2026-11-04-task-project-catalog.md)。以下“优先”均指批准方案后的候选试点次序。

| 工作问题 | 候选项目 | 可以直接复用什么 | 建议与前提 |
| --- | --- | --- | --- |
| 接手 STM32 或其他不熟悉代码 | Understand-Anything | 结构图、导览、解释、变更影响界面 | 优先评估一个小模块；先走其明确支持的 Codex 路线，DSH 不冒充原生兼容 |
| 给模型准备准确、可控的代码材料 | Repomix | 选定文件的打包与上下文组织 | 轻量试点，不先常驻 MCP；核查旧中文编码和文件完整性 |
| 经常查定义、引用、跨文件符号 | Serena | clangd 等语言服务器能力接入智能体 | 编译参数/数据库准备好后试点；不能把索引未完成的空结果当作无调用者 |
| 希望用图查询辅助影响分析 | GitNexus | 调用图、路径与影响查询 | 当前暂缓：工作用途许可条件和 Windows 稳定版问题尚需解决 |
| 扫描测试材料、复杂 PDF 表格难整理 | Docling | OCR、阅读顺序和表格结构提取 | 资料确有读取瓶颈时试点；清晰文本继续用现有能力 |
| 反复制作公司格式 PPT | Presenton | 模板化生成、可视化编辑、导出界面 | 值得产品级试点；公司模板重建和 Windows 导出必须实际验证 |
| 做介绍页、作品集、博客等小网站 | AstroWind | 现成页面、导航、博客和站点基础 | 将来做该类站点时优先复用模板，由现有 Codex 修改；有登录/业务数据库时重新选型 |
| 想在浏览器中聊天生成和预览网站 | bolt.diy | 完整 AI 搭站工作台 | 可选；会引入另一套运行环境及模型配置，不预设复用现有聊天订阅 |
| 反复从同类网站抽取资料 | Crawl4AI | 网页正文、规则抽取及批量采集 | 同类任务重复出现时试点；偶尔读几个网页优先已有能力 |
| 更愿意使用托管采集 API | Firecrawl | 搜索、抓取与结构化接口 | 服务型替代；云端与自托管功能/成本分别评估 |
| 需要长期维护多个 VPS 服务 | Coolify / Dokploy | 部署、数据库、域名、日志和更新管理 | 有明确服务器与多服务需求时二选一；本轮不连接 VPS、不部署面板 |

手工 BOM 当前没有从这些项目中找到直接替代整个流程的产品。保留现有表格能力，明确料号、规格、数量、单位、合并与版本规则；不要把爬虫或文档解析器包装成已完成 BOM 管理。

## 4. 第一批试点如何选择

不一次安装整个目录。先验证最容易证明新增价值的任务，再确定常用组合。

### A. 代码理解：Understand-Anything 与轻量路径比较

使用同一份公开或脱敏的小型 STM32 源码，事先记录启动入口、一个外设初始化、中断到回调、同名 static 函数等已知关系。比较：

- 当前直接阅读与检索。
- 通过 Repomix 组织选定材料后的阅读。
- Understand-Anything 的图谱和导览。

检查定位时间、源文件依据、错误/遗漏和人工纠正次数，以及模型用量。图形丰富不单独算通过。Serena 在编译参数可用时加入符号查询比较，不能为了试点先把完整 GCC 迁移变成前置工程。

Understand-Anything 已核实有 C/C++ 配置与 Windows/Codex 安装方式，但包含完整插件代码、构建和代理依赖，不能只复制 SKILL.md。初次分析有模型消耗；已有图文件的只读查看器条件不同。

还需核对源目录与提交。上游 issue #739 报告 worktree 重定向可能漏掉分支文件；首次试点优先普通独立 checkout，使用 worktree 时专门验证该行为。详见 [案例评估](../research/2026-11-04-understand-anything-assessment.md)。

### B. 报告与 PPT：现有能力和成熟产品同题比较

用户管理工作最常发生，先用当前办公能力完成一份报告与汇报样例。随后仅针对耗时环节比较：

- 资料难读取：试 Docling，核对数字、单位、表格和来源完整性。
- PPT 反复制稿与调整：试 Presenton，检查模板效果、字体、可编辑性、导出和本地操作成本。
- 需要独立于宿主的稳定 PDF 导出：评估 Pandoc + Typst。

已有能力若满足任务，不重复安装底层库；成熟产品若明显改善操作与返工，就纳入组合。Presenton 的桌面界面、Docling 的结构化解析是应比较的新增能力，不应仅因本机已有办公 Skill 就排除。

### C. 小网站：优先套用完整模板

当用户有具体网站需求时，先判断属于展示/博客、交互工具，还是需要账号与数据库的业务应用。

展示/博客优先从 AstroWind 这样的现成模板试起：本地生成、由 Codex 修改内容和组件、构建并检查移动端。Understand-Anything 可用于接手较复杂的现有代码，但不是网站模板本身。

bolt.diy 在用户确实需要浏览器内 AI 搭站工作台时才进入比较。第一次上线按实际构建产物选托管方式；多服务运维成为痛点后，再评估 Coolify 或 Dokploy。

## 5. 如何持续挖掘，而不依赖一次推荐

工程需要沉淀一套可复用的发现记录，每个候选至少回答：

1. **任务匹配**：输入是什么，输出是什么，替代当前哪一步。
2. **成熟形态**：完整产品/模板、CLI/MCP、Skill，还是需要再开发的库。
3. **使用证据**：维护与发布、Stars/下载的准确含义、真实用户案例和问题；作者宣传单独标注。
4. **适配条件**：Windows、Codex、DSH、C/C++、文件格式、必要账号与运行时。
5. **接入成本**：部署、配置、模型用量、硬件、维护，以及与现有工具的功能重复。
6. **结果验证**：源依据、错误、遗漏、返工、人工步骤、相同任务的时间比较。
7. **采用决定**：推荐试点、通过后采用、条件不足、暂缓或淘汰，并保存原因和日期。

不建立“Stars 越高得分越高”的自动排序。对候选的许可按当前官方文件标注；例如 GitNexus 与部分 source-available 技能不能因为 GitHub 可见就统一按不限用途的开源工具处理。

别人首次使用时允许出现当前目录外的新任务。访谈后应继续寻找并补证据，不能把作者的 STM32/PPT 组合强加给所有人。

## 6. 开发者实践如何用在这里

抽样到的实际工作方式包括：简短项目规则与现成 CLI、小步实现并运行检查、将高频流程封装成仓库技能，以及为较复杂变更增加规范文档。社区对技能数量和流程强度存在分歧，没有证据支持一套配置适合所有人。

因此日常采用：

- 轻任务：目标、输入、验收条件明确后直接使用合适工具。
- 复杂开发：保留现有 Superpowers 的需求、计划、实现、验证与评审流程。
- 长期迁移：先记录目标、状态、下一步与验证；确有需要再在单项目试用 OpenSpec 等工具。
- 反复有效的流程：先保存工作说明，经过重复使用再封装 Skill，不预先编写一批空泛的新技能。

`grill-me/grilling` 继续承担需求澄清。`grill-with-docs` 可作为带决策文档的替代候选，但需要同时检查其 grilling、domain-modeling 依赖和宿主调用方式。

实践与社区来源见 [开发者实践调研](../research/2026-11-04-community-workflows.md)，流程框架与管理器比较见 [第二轮工具比较](../research/2026-11-04-tooling-comparison-v2.md)。

## 7. 全局管理只做支撑，不强制所有项目同一种安装方式

| 资源类型 | 负责安装/更新的一方 | 工程如何记录 |
| --- | --- | --- |
| 普通独立 Skills | 固定版本 Vercel Skills CLI | 完整提交、技能子路径、作用范围、依赖与校验 |
| Codex 原生插件 | Codex 插件管理器 | 插件来源、版本策略、获得方式与验证结果 |
| Understand-Anything 这类完整项目 | 该项目受支持的安装与构建方式 | 仓库/发布版本、专属路径与技能名、依赖、更新行为、恢复级别 |
| 网站模板 | 各网站项目自己的 Git 与包管理器 | 模板来源、起始提交、项目修改与构建记录 |
| 自托管服务 | 目标服务器的原生部署方式 | 镜像/版本、配置模板、部署前提；凭据另行管理 |
| 模型供应商与 MCP | CC Switch/客户端官方接口 | 不含密钥的配置模板、依赖和实际连接状态 |

同一个目录或命名空间只有一个负责方。Understand-Anything 的专属安装器会创建技能链接和插件根目录，就不能再让 Skills CLI 或 CC Switch 同步这些同名条目。全局管理统一的是选择、来源、归属和验证记录，不是把所有产品转换成 SKILL.md。

每个完整项目的接入步骤必须列出将占用的技能名、目录、服务/端口及更新方式，检查与既有安装是否冲突后再执行。项目生成的图、报告和索引保存在相应项目或本机私有位置，不因工具链工程要公开就自动提交真实业务产物。步骤还应写清哪些输入由本机处理，哪些会交给已配置的模型或外部服务；只读查看器的本地特性不能套用到首次分析过程。

特别是 Understand-Anything：其安装器选择 Codex 仍会写入共享 `.agents/skills`。据 DSH 的扫描契约推断，这些入口可能同时对 DSH 可见；“入口可见”和“流水线已兼容”必须分别记录。首轮单宿主试点放在完整隔离环境，避免未验证技能进入日常 DSH 目录。正式接入需核对预期/实际可见客户端；没有验证过宿主过滤机制时，不承诺可以只向 Codex 暴露。

当前基础建议：保留 Codex、DSH、Superpowers 与本地 grilling；备份并升级 CC Switch 到已核验有 DSH 接入的 v4.0.25 后做本机验证；普通 Skills 采用核查过的 `skills@1.7.6` 作为候选管理入口。其他项目按试点结果加入。

Skills CLI 本次版本没有 DSH 专用目标，不能写 `--agent dsh`。其 Codex 目标使用共享 `.agents/skills`，DSH 对应版本也有读取契约；实际发现仍取决于插件启用、来源目录和同名覆盖。普通技能的双端支持与复杂产品的原生接入分别验证。

CC Switch 的内部 Tauri 函数不当成稳定外部 CLI；无法自动化的步骤明确提供原生 UI 指引，不直接写数据库。

## 8. 双入口与数据契约

仓库用少量 JSON 保存选择与来源，用 Markdown 保存理由和验收，不实现新的通用包管理器。

### 8.1 必须关联起来的数据

| 记录 | 最小字段 | 责任 |
| --- | --- | --- |
| 能力目录 | capability_id、任务、候选实现、证据与日期 | 描述用户需要的能力，不绑死单一工具 |
| 个人选择 | schema_version、capability_id、implementation_id、source_id、required_targets、必要/可选、verification_id | 两个入口都产生这一格式；目标由用户需求确定 |
| 来源锁定 | source_id、类型、上游、精确版本/完整提交或宿主管理模式、技能子路径、owner、scope、依赖、恢复级别、校验状态 | 区分候选与确实可恢复的来源 |
| 安装计划 | 源记录引用、实际目标、前置检查、动作类型、归属检查、人工步骤、验证项 | 只消费已确认的个人选择；不重新猜测版本 |
| 验证报告 | verification_id、输入、源版本、客户端、结果、证据、人工操作、错误与成本 | 明确文档支持/已装/已发现/任务通过等状态 |

### 8.2 三类贯通示例

**固定上游的普通技能**：访谈选中某项 → 个人选择引用 `source_id` → 源记录含完整提交、仓库中的技能子路径与依赖 → 固定 CLI 安装到选定范围 → 比对该技能包内的文件清单与 SHA-256 → 两个客户端分别验证。

校验范围包括 SKILL.md 和被安装的 scripts/references/assets 等包内文件。生成缓存、node_modules、日志和宿主外部运行时不冒充技能包内容，单独按依赖记录。期望清单应从选定不可变来源取得，不能只给本机现有文件算哈希就声称匹配上游。

**本地修改的 grilling**：个人选择引用 `private-grilling` → 来源类型为 private-local → 私有映射指定 `root_key=personal_skills` 和相对路径 `grilling` → 安装前解析用户提供的根目录并核对文件清单。拒绝路径越界；缺少根映射或文件时列为需要人工提供。公共仓库没有这些私有文件，也不能用通用示例冒充恢复成功。

**Codex 办公插件**：个人选择引用宿主办公能力 → 来源类型为 host-managed → 记录插件标识、获得途径和版本策略 → 使用原生方式恢复 → 完成报告/PPT/BOM 样例。本会话虽已发现技能入口，但完整恢复来源尚未核对，当前必须保持“恢复来源待核实”，不能虚构插件 ID。

Understand-Anything 属于完整项目来源：本次观察到提交 `4e6d3299017a7432da15957874992837a315c5b4`，但官方安装器默认克隆/拉取，并未在本轮验证按该提交恢复。因此记录为“观察到的源码 + 官方引导恢复候选”，不冒充已实现精确锁定。

例如，本地需求访谈能力的个人选择可以采用如下结构（这是数据契约示例，不是已生成的安装清单）：

```json
{
  "schema_version": 1,
  "capabilities": [{
    "capability_id": "requirements-interview",
    "implementation_id": "local-grilling",
    "source_id": "private-grilling",
    "required_targets": ["codex", "dsh"],
    "required": true,
    "verification_id": "interview-smoke-v1"
  }]
}
```

`private-grilling` 在私有来源记录中关联 `root_key=personal_skills`、相对路径 `grilling` 和文件清单；其校验状态在采集前为 `pending-capture`，不可直接生成安装动作。解析并确认私有源后才生成计划，验证报告继续引用 `interview-smoke-v1`，分别记录两个客户端结果。

如果某工具只支持 Codex，不能把用户要求的 `required_targets=[codex,dsh]` 自动缩成 Codex。应保留为缺口、寻找另一实现或由用户另行决定范围；共同能力底座与客户端专属扩展分别验收。

### 8.3 入口 A：本人恢复

获取仓库版本与个人选择 → 提供必要私有根映射 → 检查系统/宿主/路径/归属 → 生成计划 → 确认后调用受支持的安装方式 → 正常登录和完成必要 UI 步骤 → 逐项报告结果。

### 8.4 入口 B：首次访谈推荐

通过普通 Markdown 访谈入口确认工作与约束 → 查现有目录或继续调研新项目 → 解释方案与成本 → 生成相同格式的个人选择 → 经确认进入同一套计划与验证流程。

推荐入口不要求先安装一个新 Skill，也不额外购买 AI 服务。成熟后可以再封装入口，但不作为首版前提。

## 9. 恢复等级与隔离演练

恢复不能用一个“成功”字段概括：

- **精确来源可核查**：固定普通技能/CLI 版本，并验证预期内容。
- **宿主/上游管理**：应用或插件按官方方式恢复，记录实际版本并重测。
- **人工步骤**：账号、部分 GUI 配置、私有文件需要提供或操作。
- **未完成/不支持**：缺少依赖、宿主不支持、任务失败，明确记录。

固定来源失败不静默退回 HEAD/latest；未经纳管、不同来源或本地修改的同名内容不自动覆盖；内容相符的项跳过。原生插件与完整项目只由其明确负责人修改。

**纠正第二版的隔离问题：改变工作目录并不能隔离全局技能、锁文件和客户端状态。**

因此需要执行安装的恢复演练，采用独立 Windows 测试用户、可丢弃虚拟机或可用的 Windows Sandbox 等完整账户边界。需覆盖技能根目录、CLI 全局锁/配置、用户缓存、客户端配置及应用数据；不通过改写全局 HOME/CODEX_HOME 或清空真实配置制造“新电脑”。

在当前真实账户内只进行已批准的实际安装与只读检查，不将全局写入伪装成隔离测试。项目范围测试若涉及 CLI 全局状态，同样进入完整隔离环境。无法提供隔离环境时，恢复演练标记为未执行；文档检查与一次本机成功安装都不能替代它。

全局恢复在隔离环境通过，也仍区别于用户另一台实际电脑上的验证。

## 11. 执行与验收顺序

方案批准后按以下阶段进行；本轮不执行安装。

1. **建立可复用发现入口与目录**：保留现有调研，落实能力选择、证据和来源记录，完善模板与只读检查。
2. **确定并执行一个任务试点**：建议优先代码理解或实际最耗时的报告环节；没有用户真实样例时用公开/合成输入，明确结果范围。
3. **把有效工具纳入组合**：保存安装与使用步骤、依赖、负责方、版本与验证。失败的候选也保留原因，不默认继续增加工具。
4. **完成基础集中管理**：在批准范围内备份/升级 CC Switch，处理普通 Skills 和专属项目的归属，分别验证 Codex/DSH。
5. **恢复演练与公开准备**：按完整隔离边界演练，检查公开文件与私有材料分离；本地可审阅后确定远端平台、仓库名和公开范围。

最少验收内容：

- 同一任务的旧做法与候选工具：源依据、错误/遗漏、返工、人工操作、耗时和模型/运行成本。
- 安装行为：明确来源、目标路径、负责人、失败处理和重复执行。
- 双端能力：普通共享技能在两端分别发现并调用；复杂项目按支持矩阵验证，不用 Codex 成功代替 DSH 成功。
- 资料成果：中文 PDF、可编辑 PPT、BOM 差异与来源记录；合成样例与真实业务样例分开标注。
- 网站成果：只在有相应任务时验证本地构建、主要页面与移动端；部署另按选定托管方式验收。
- 恢复结果：私有文件缺失、错误来源、同名内容与人工登录都有明确结果；测试隔离记录可检查。
