# 第二版方案严格评审记录

日期：2026-11-04（Asia/Shanghai）。评审对象：[第二版方案](../design/2026-11-04-ai-toolchain-design-v2.md)。

本记录审查设计与来源证据，不代表安装、双端运行或换机测试已经通过。用户要求在提交新方案前单独严格审查；本轮先完成作者自查，再交独立上下文审阅。

## 1. 评审准则

1. 是否完整保留已确认需求：双入口、Windows + Codex + DSH、现有账号优先、三个工作方向。
2. 推荐是否有可读来源；是否区分宣传、使用反馈、源码支持与本机实测。
3. 是否优先复用成熟工具，避免重写安装/同步逻辑或先造未验证技能。
4. 是否存在目录写入冲突、假想命令、未闭合的技能依赖或错误的版本固定承诺。
5. 是否能解释恢复中的个人文件、原生插件、账号与人工步骤。
6. 验收是否能揭示实际失败，而非仅检查文件生成或命令退出。

## 2. 写完后的作者自查

主任务重新完整阅读方案，并逐项对照用户需求及官方来源，发现并修正如下问题：

| 编号 | 程度 | 原问题 | 修正 |
| --- | --- | --- | --- |
| S1 | 重要 | 记录来源与版本的字段过于抽象，可能出现声称锁定却没有校验或负责人 | 补充工具目录、来源锁定和个人选择的最小字段；缺失验证的条目明确作为候选 |
| S2 | 重要 | “使用已有办公能力”可能被误读为新电脑一定能恢复同一插件 | 要求记录插件来源与获得途径；新环境不可获取时标缺口，不能搬运私有运行时 |
| S3 | 重要 | 固定了入口文件仍可能遗漏被调用的其他技能或工具 | 以实际读取的 grill-with-docs 为例补充依赖闭合检查 |
| S4 | 重要 | 只写单一管理者原则，未明确同名本地修改如何阻止安装器覆盖 | 补充安装前归属与内容检查；未知/不同内容停止，匹配项跳过，不做自动合并 |
| S5 | 改进 | 验收强调技术通过，没有衡量是否减少实际工作 | 补充人工步骤、错误、返工与同条件比较，不凭印象宣称效率提升 |

另核对：不能使用不存在的 `--agent dsh`；不能把实验性项目锁文件恢复解释为全机恢复；不能将 source-available 办公技能视为可自由再分发；CC Switch 的 DSH 支持按 v4.0.25 发布源码判断，而不是按旧版本猜测。

## 3. 独立审阅

独立审阅已完成，只读方案、需求和研究材料，未参与写作、未修改工作区。

审阅期间用户补充了 Understand-Anything 案例，明确希望围绕实际任务寻找成熟 GitHub 项目。第二版因此作为中间稿结束，不作为最终提交方案。

独立审阅结论：未发现有充分依据的 Critical 问题；有三项 Important，需要在第三版解决。

| 编号 | 发现 | 第三版必须处理 |
| --- | --- | --- |
| I1 | 第二版过度偏重管理和减少安装，嵌入式理解、小网站等成熟任务项目挖掘不足 | 以任务为中心比较成熟项目，管理层只作支撑 |
| I2 | 隔离目录演练没有说明技能目录、全局锁与客户端状态怎样全部隔离 | 项目范围与全局恢复分别定义；全局测试使用独立 Windows 用户/虚拟机等完整边界，不能仅改变工作目录 |
| I3 | 访谈选择、来源条目、私有文件和安装计划之间缺少贯通数据示例 | 提供固定上游、私有技能、宿主插件三类引用与状态流，不扩成通用配置引擎 |

已确认的设计优点：双入口和工作场景仍保留；Skills CLI 的固定提交源码与 DSH 目录机制有依据；已有办公入口与可恢复性的界限表达正确。

最终判定：**第二版未通过最终提交评审，需要第三版重写后重新审查。**
